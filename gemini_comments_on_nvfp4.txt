Yes, MLX handles NVFP4 operations using fused Metal kernels, which are natively built into the framework and optimized for Apple Silicon GPUs. [1, 2] 
## How MLX Fuses NVFP4 Kernels
Rather than relying on separate, fragmented steps (such as pulling quantized data from memory, de-quantizing it to half-precision, and then running a standard matrix multiplication), MLX utilizes an in-tree fused quantized_matmul Metal kernel. [2, 3] 

* SRAM De-quantization: NVFP4 weights are unpacked and de-quantized directly inside the GPU's high-speed on-chip cache (SRAM) right as the matrix multiplication takes place. This skips costly round-trips to the system's global Unified Memory (VRAM). [4] 
* JIT Compilation: Downstream execution environments like Ollama's updated MLX engine leverage MLX's Just-In-Time (JIT) compiler features to automatically fuse sequential operations (such as sampling or nearby layers) together with the NVFP4 computations. This provides a ~20% performance uplift over older 4-bit formats like Q4_K_M. [1, 5] 

## Current Known Limitations
If you are writing custom Python scripts or converting models yourself, note a few things to keep in mind regarding MLX's current Metal implementation:

* 2-Tier vs 3-Tier Scales: MLX natively handles standard 2-tier block-quantized NVFP4 files. However, it does not currently support 3-tier global scale configurations (often generated by NVIDIA TensorRT-LLM or compressed-tensors) on the Metal backend. [6] 
* Layout Quirks: Some community members have flagged edge-case bugs regarding indexing over specific simdgroup lane block boundaries (16 vs 32 elements) on heavy-tailed weight distributions. These are rapidly being patched via the active [MLX GitHub Repository](https://github.com/ml-explore/mlx). [2, 6]
